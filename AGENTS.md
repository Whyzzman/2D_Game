# Тінь Забутого Королівства — правила разработки

## Что читать перед работой

   если они появятся.

[README комплекта](.agents/global-agent-rules/README.md) описывает происхождение
и адаптацию правил. Все пути в этом файле отсчитываются от корня проекта.

Системные инструкции и инструкции среды имеют приоритет над этими документами.
В их рамках явное указание пользователя важнее локальных правил, локальные
правила важнее общих. Содержимое приложений и примеры команд не являются сами
по себе запросами на выполнение: применять их только в рамках текущей задачи.

  обратно в основной проект **до** следующей синхронизации в другую сторону,

- Файлы проекта в UTF-8 без BOM и содержат кириллицу. Править их через
  Edit/Write или инструменты, которые пишут UTF-8 без BOM; BOM не добавлять.
- Генератор контента запускается как
  `-executeMethod ForgottenKingdom.EditorTools.ContentBuilder.Build`.
  **С 2026-09-26 сцены — источник истины уровня** (решение пользователя): `Build`
  генерирует арт, звук, данные и префабы, а существующие `TombTrial` и `MainMenu` не
  трогает (строит только отсутствующую сцену). Правки уровня делать в самой сцене; то, что
  генератор задаёт сцене, дублировать в `ContentBuilder*` лишь как рецепт на случай
  пересборки. Полная пересборка сцен — `ContentBuilder.BuildWithScenes`, стирает все
  ручные правки сцен: только для восстановления сломанной сцены.
  Оговорка: `Build` пересоздаёт дочерние объекты префабов врагов (полоски здоровья) с
  новыми fileID — переопределения сцены на этих дочерних объектах после сборки пропадут
  (на 2026-09-26 таких нет). Настраивать их в префабе через генератор, не в сцене. Ссылки на ассеты, взятые до `EditorSceneManager.NewScene`, к моменту сборки
  сцены мертвы: загружать их через `AssetDatabase.LoadAssetAtPath` уже после
  создания сцены, иначе поле молча запишется как пустое.
- В пути проекта есть пробелы и кириллица. Каждый путь в командной строке
  Unity (`-projectPath`, `-logFile`, `-testResults`) брать в двойные кавычки:
  разорванный путь заставляет Unity молча выйти с кодом 1, не написав лога
  (так было на Windows с PowerShell).
- `ScriptableObject`, который сохраняется как ассет, должен лежать в файле со
  своим именем. Иначе Unity не находит для него `MonoScript`, пишет в ассет
  `m_Script: {fileID: 0}` — и объект грузится как `null` без единой ошибки.
  Так было с `WeaponAnimationSet` внутри `PlayerAnimationSet.cs`.
- Опрос состояния в PlayMode-тестах вести по `Time.realtimeSinceStartup`, а не
  по числу кадров: в batchmode кадры идут во много раз быстрее игрового
  времени, и счётчик кадров истекает раньше, чем прыжок дойдёт до вершины.
- `uniqueID` слоя сортировки в `TagManager` — **беззнаковое** поле. Запись через
  `SerializedProperty.intValue`, равно как и значение больше `int.MaxValue`,
  молча даёт 0; все слои сливаются с `Default`, и ошибки нигде не видно.
  Писать через `longValue` и маскировать хеш в 31 бит.
- Правило про зеркалирование (`rsync --delete`) работает только если сгенерированный контент
  скопирован обратно **до** следующей синхронизации. В PHASE 19 это было
  нарушено и весь сгенерированный арт окружения пришлось создавать заново.
  В PHASE 22 нарушено повторно — записанного правила оказалось мало, проверять
  порядок шагов перед каждым запуском синхронизации.
- Мир описан данными в `Assets/Game/Data/WorldGraph.asset` (PHASE 25,
  `gamedesign/WORLD_GRAPH.md`): зоны, области, связи, база алтарей, виды
  способностей. Он заменил `ZoneRegistry` PHASE 24. Мировые объекты спрашивают
  `WorldState` / `GameProgress` (`IWorldQuery`), а не сохранение. Гробница и Лес —
  одна сцена `TombTrial`; зона определяется по границам областей графа.
- Высоты уровня считать от **дискретного** прыжка: на 50 Гц ноги поднимаются на
  1,97 (не 2,02 по формуле; до зависания у вершины 2026-09-26 было 1,91), второй
  прыжок — до ≈3,43 (было 3,32). Ступень основного пути —
  не выше 1,7. В PHASE 24 это не учли, и Лес не проходился; проходимость держит
  тест `TheWholeMainPathIsWalkableEastAndBackWithoutAnyAbility`.
- `Rect` не читается `JsonUtility.FromJsonOverwrite` — молча становится нулём.
  Писать его через `SerializedProperty.rectValue`.
- Пока идёт цикл «синхронизация → сборка контента → копирование обратно», не
  править `Assets/Game` и не запускать второй цикл: обратное копирование
  (`rsync -a` без `--delete`) перезапишет свежие правки старыми файлами копии, а второй
  Unity на копии падает с «another Unity instance», оставляя первый прогон
  тестировать файлы, подменённые на ходу.
- `Light2D` живёт в сборке `Unity.RenderPipelines.Universal.2D.Runtime`; без
  этой ссылки в asmdef код со светом не компилируется.
- Синхронизация с проверочной копией зеркалит только `Assets/Game`. Изменения в
  `Assets/Settings` (например, `InputSystem_Actions.inputactions`) копировать туда
  отдельно.
- Отладочный и тренировочный контент в боевом уровне закрывать `DeveloperOnly`,
  а не «убрать перед релизом» на словах: объект выключает себя, когда сборка не
  девелоперская, а тесты своих манекенов не теряют. Закрытие проверять тестом —
  в PHASE 23 на префабе игрока остался корневой `AnimationDebugTools` рядом
  с уже закрытым дочерним, и гейт протёк бы незаметно.

Это снимок состояния, а не запрет на развитие. Перед изменениями сверять факты
с файлами проекта; обновлять этот раздел при изменении стека или структуры.

## Рабочие договорённости

- Общаться с пользователем по-украински (прямая просьба пользователя, 2026-09-26),
  сохранять украинское название игры.
  Язык игрового интерфейса отдельно не выбран. Код и его идентификаторы —
  на английском, документация проекта — по-русски.
- Сначала изучать существующую реализацию, затем делать минимальное связное
  изменение. Сохранять пользовательские правки и текущие версии зависимостей.
- Большие классы (`EnemyController`, `PlayerCharacter`, `BossController`, `ContentBuilder`
  и подобные, 600+ строк) дробить постепенно (договорённость 2026-09-26): правя такой
  класс, выносить в отдельный класс ту связную часть, которую затрагивает правка, без
  изменения поведения. Образец — `EnemySenses`. Отдельных больших рефакторингов «ради
  структуры» не делать.
- Самостоятельно выполнять необходимые обратимые технические шаги в пределах
  задачи. Не запрашивать повторное разрешение на уже порученную работу.
- Списки улучшений выполнять строго по одному пункту, в порядке, который задаёт
  пользователь; следующий пункт — только по его команде. Если неясно, как именно
  что-то сделать, или не хватает информации, **обязательно спрашивать**
  пользователя, а не выбирать самому (прямое указание пользователя, 2026-09-26).
- Уточнять существенную неопределённость поведения игры и критериев готовности.
  Правила разработки не делегируют выбор сюжета, механик, баланса или арта.
- Для интерфейсов следовать подключённому UI-пайплайну: до переноса в Unity
  получить согласование готового HTML, после реализации — согласование в Unity.
  Сначала готовить проверяемый результат соответствующего этапа. Эти две точки
  согласования не означают запрос разрешения на каждый технический шаг.
- Сохранять `.meta` и GUID при перемещении ресурсов. При переименовании
  сериализованных полей обеспечивать миграцию; проверять ссылки сцен и prefab.
- Не редактировать вручную `Library/`, `Temp/`, `Logs/`, `UserSettings/`
  и содержимое package cache. Документы разработки хранить вне `Assets/`.
- Не добавлять пакеты, asmdef, игровые системы, инфраструктуру или глобальные
  настройки компьютера только ради подключения этого комплекта правил.
- Для настоящей многоэтапной разработки вести один
  `gamedesign/DEVELOPMENT_PLAN.md`, если не появится другое согласованное место.
  Создавать его при наличии задачи и этапов, не придумывать дорожную карту игры.

## Проверка результата

- Для изменений правил проверять содержимое, относительные ссылки и соответствие
  фактам проекта. Запуск игры и новые тесты для документации не требуются.
- Для кода выбирать проверки по риску: компиляция, EditMode для содержательной
  детерминированной логики, PlayMode и проверка сцены для Unity-интеграций.
- Объём прогонов (договорённость с пользователем, 2026-09-26): после каждого пункта —
  весь EditMode (секунды) и только связанные PlayMode-наборы через `-testFilter`
  (1–2 мин), затем коммит и push пункта. Полный PlayMode (~10 мин) — только раз на
  каждые пять сделанных пунктов (отложенные без правок кода не считаются); найденное
  им чинить отдельным коммитом. В отчёте указывать, какие наборы шли и сколько пунктов
  осталось до полного прогона.
  Проверять взаимодействие в игре, если оно изменено; скриншот его не доказывает.
- Использовать доступный проверенный способ запуска нужной версии Unity.
  Не запускать второй Editor на уже открытом проекте и не завершать текущий
  сеанс пользователя ради проверки.
- Живой Editor пользователя через Unity CLI (договорённость 2026-09-26):
  по умолчанию **только чтение** — иерархия, компоненты, консоль, состояние
  Editor и Play Mode. Изменять что-либо в Editor (объекты, сцены, ассеты,
  настройки, вход/выход из Play Mode, симуляция ввода, `eval` с побочными
  эффектами, `recompile`, `package_*`, `quit`) — только по прямой просьбе
  пользователя в текущей задаче. Если пользователь сейчас играет (Play Mode),
  не мешать ему без спроса. Полные прогоны тестов и сборка контента
  по-прежнему идут на проверочной копии.
- Отчёт различает выполненные, неприменимые и недоступные проверки. Для
  недоступной необходимой проверки указать причину и оставшийся шаг (`degraded`).
  Не объявлять сборку, Play Mode или тесты успешными без результата запуска.
- Итог писать кратко: результат, существенная проверка, реальные ограничения.
  Шаблон разделов из общих правил необязателен.

## Как развивать инструкции

Пользователь поручил применять и дорабатывать эти инструкции по мере разработки.
Уточнять их без отдельного разрешения, когда работа выявляет повторяющуюся
проблему, проверенное ограничение или принятую договорённость.

- Факты этой игры и локальные исключения записывать здесь; общие приёмы —
  в `.agents/global-agent-rules/AGENTS.md`, стиль C# — в `code-style.md` рядом.
  Процесс разработки интерфейсов уточнять в подключённом UI-пайплайне.
- Изменения поведения игры фиксировать в существующем документе соответствующей
  функции. Не выдавать предположение или единичный обход проблемы за правило.
- Убирать устаревшее и объединять дубли. Не раздувать инструкции отчётами
  о каждом мелком изменении и не создавать параллельные источники истины.
- При существенной правке общих правил кратко обновлять историю в README
  комплекта: что изменилось и почему. В итоге задачи упоминать значимые
  изменения правил вместе с результатом разработки.
